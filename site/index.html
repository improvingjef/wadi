The Manifest

One file. That's it.

Everything your project needs in a single, readable wadi.toml. No ceremony. No implicit rules. No surprises.

Radically simple

Declare your libraries, executables, and tests. Wadi handles the rest—module ordering, dependency closure, package resolution, compiler flags. You describe what you're building, not how.

  • Automatic module ordering via ocamldep
  • Transitive dependency resolution with cycle detection
  • External package propagation through library deps
  • Build profiles with per-target overrides
  • Validated at load time with clear error messages
  • No hand-maintained module lists. Ever.
wadi.toml 
workspace = "myproject"
version   = 1

# A library with external packages
[library.core]
dir      = "lib"
modules  = ["engine", "parser", "types"]
packages = ["unix", "str"]

# An executable that depends on it
[executable.app]
dir  = "bin"
main = "main"
deps = ["core"]

# Tests that exercise the library
[test.unit]
dir  = "test"
main = "test_main"
deps = ["core"]

# Build profiles with per-target overrides
[profile.release]
compile_flags = ["-O2", "-unbox-closures"]

[profile.release.executable.app]
link_flags = ["-noassert"]

The Toolkit

31 commands. Zero confusion.

Each command does one thing and does it well. Here are the ones you'll reach for most. Composable through stable files and exit codes. No hidden state, no global caches, no magic.

wadi build
[--backend auto|native|bytecode] [--verbose] [TARGET ...]

Compile libraries, executables, and tests with content-based incremental builds. Resolves dependencies, infers module order, propagates packages. Just works.

wadi run
[TARGET] [-- ARG ...]

Build and launch executables with exact argv semantics. Direct process spawning—signals, streaming IO, and exit codes preserved. No shell wrapping.

wadi test
[TARGET ...]

Discover and run test targets with TAP-style output. Builds before running. Clear pass/fail summaries with exit codes and failure details.

wadi clean
[TARGET ...]

Remove build artifacts. Full workspace wipe or surgical per-target cleanup. Prunes empty directories automatically.

wadi explain
[--profile NAME] [TARGET ...]

Understand why targets rebuilt. Shows fingerprint diffs, compiler invocations, and include paths. The build system that explains itself.

wadi install
[--prefix DIR] [--destdir DIR] [TARGET ...]

Stage libraries, executables, and metadata for distribution. Generates META files, resolves transitive closures, supports DESTDIR for package-manager staging.

wadi toolchain
(no arguments)

One-stop diagnostic view of your OCaml environment. Compiler paths, backend selection, stdlib location, package roots. Never wonder "which ocamlopt?" again.

wadi watch
[--profile NAME] [TARGET ...]

File-watching rebuild loop. Monitors source files and the manifest, re-running incremental builds automatically when anything changes.

wadi init
[--lib | --exe | --full] [NAME]

Scaffold a new project. Generates a wadi.toml and starter source files so you can go from zero to building in seconds.

wadi doctor
(no arguments)

Workspace health checks. Validates the manifest, verifies toolchain availability, checks for stale artifacts, and reports any issues.

wadi lock
[--update]

Snapshot exact toolchain versions and package resolutions into a lockfile. Reproducible builds across machines and CI.

wadi repl
[TARGET] [-- OCAML_ARG ...]

Launch a bytecode toplevel with workspace libraries and packages already wired in. Interactive exploration, zero setup.

wadi migrate
[--output PATH] [--stdout] [--force]

Scan dune files and generate a first-pass wadi.toml with review comments for anything that needs attention.

wadi format
[--workspace DIR] [--check] [TARGET ...]

Auto-format OCaml source files via ocamlformat. Use --check to verify formatting without writing changes—perfect for CI gates.

wadi lint
[--workspace DIR] [--profile NAME] [TARGET ...]

Run strict compiler warnings across your workspace. Surfaces issues that normal builds miss by enabling a stricter warning set.

Under the Hood

Engineered with intention

Content-Based Fingerprints

Wadi tracks manifest hashes, source digests, compiler versions, and toolchain state. Rebuilds happen when something actually changes—not when a timestamp drifts.

Cycle Detection

Dependency cycles are caught at manifest load time with clear diagnostic messages. No cryptic compiler errors an hour into your build.

Transitive Closure

Library dependencies are fully resolved. External packages flow through the dependency graph automatically. Declare once, link everywhere.

Backend Flexibility

Native by default, bytecode fallback, or explicit selection. Wadi detects what's available and makes the right call—or lets you override it.

Build Profiles

Define custom profiles with workspace-wide defaults and per-target overrides. Separate artifact roots per profile. No more flag juggling.

Build Diagnostics

wadi explain tells you exactly why a target rebuilt—fingerprint diffs, compiler invocations, include paths. No more guessing.

Multi-Package Workspaces

Split large projects into member packages with scoped tools and shared dependency analysis. Each member owns its targets while inheriting workspace defaults.

Install & META Generation

Stage libraries and executables with automatically generated findlib META files. DESTDIR support for clean package-manager integration.

Self-Hosting Bootstrap

Wadi generates its own Makefile from its own manifest. No circular bootstrap dependency. Pure OCaml all the way down.

File-Watching Rebuilds

wadi watch monitors your sources and manifest, re-running incremental builds the moment anything changes. Instant feedback loops.

Project Scaffolding

wadi init generates a wadi.toml and starter files. Go from zero to building in seconds—no boilerplate to copy-paste.

Workspace Health Checks

wadi doctor validates your manifest, verifies toolchain availability, checks for stale artifacts, and reports issues before they bite.

Reproducible Lockfiles

wadi lock snapshots exact toolchain versions and package resolutions. Same build on your laptop, CI, and your teammate's machine.

Library Namespace Wrapping

Set wrapped = true on a library to generate a namespace wrapper module. Clean public APIs without manual prefixing.

Automated Dune Migration

wadi migrate reads your dune files and produces a first-pass wadi.toml with review comments for anything that needs attention.

Philosophy

Built on principles

◈

Composable

Each tool owns one job. Stable files and exit codes are the interface. Compose freely.

☼

Transparent

Predictable artifact paths. Visible compiler invocations. No hidden caches. No shadow trees.

♦

Explicit

Packages, compilers, backends—declared, not guessed. If it matters, it's in the manifest.

✦

Minimal

Do the core things perfectly. Focused tools that nail it beat bloated ones that don't.

Design Choices

Intentional trade-offs

Wadi makes deliberate choices that differ from other build systems. Here's what they are and why.

Globally Unique Target Names

Target names must be unique across the entire workspace, not scoped per directory. This eliminates ambiguity in dependency references and CLI commands—when you say wadi build foo, there's exactly one thing it can mean.

Shared Library/Executable Namespace

Libraries and executables share the same naming namespace. You cannot have a library and an executable both called core. This keeps dependency resolution simple and prevents confusing shadowing scenarios.

Explicit Executable Sources

Executables only compile their declared main module and explicit modules list. They do not implicitly inherit other source files from their directory. This avoids surprises where stray .ml files silently join the build.

Actions for Menhir/ocamllex

Parser and lexer generators require explicit action definitions rather than built-in magic. This keeps the core build model simple and uniform. First-class menhir and ocamllex support is in progress.

Flat Modules by Default

Library modules are flat (unwrapped) by default—each module is globally visible by its file name. Set wrapped = true on a library to generate a namespace wrapper module when you want a clean public API boundary.
